# Mailbox Order Manager

An internal tool for selling pre-warmed Google and Microsoft mailboxes. Customers place orders (domain,
provider, 1–50 mailboxes); a background worker provisions them through mocked provider APIs; admins
see every order, its per-mailbox status and audit log, and retry failed orders.

- Order creation is idempotent (`idempotencyKey` per form, unique per customer).
- Status flow `PENDING → PROVISIONING → ACTIVE | FAILED`, admin retry `FAILED → PENDING`. Invalid
  transitions are rejected and every transition is written to an audit log in the same transaction.
- Any number of workers can run: each claims orders with `SELECT … FOR UPDATE SKIP LOCKED`, so an
  order is never processed twice.

**Stack:** Next.js 16 (App Router, strict TypeScript), React 19, PostgreSQL 16 (Docker), Prisma 7,
zod, JWT sessions (jose) with bcryptjs password hashes, Tailwind + shadcn/ui, Vitest.

Design and patterns: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). How this was built with Claude
Code: [docs/AI_WORKLOG.md](docs/AI_WORKLOG.md).

## Prerequisites

- Node.js 20.19+, 22.12+ or 24+ (Prisma 7's requirement)
- Docker with Compose v2 (`docker compose`), with Docker running
- Free ports: 5433 (Postgres) and 3000 (app)

## Quick start (clean clone, about 5 minutes)

Run from the repository root. Most of the time goes to `npm install` and pulling the Postgres image.

```bash
# 1. Setup
cp .env.example .env            # the defaults work as-is
docker compose up -d --wait     # Postgres 16 on localhost:5433; returns once it accepts connections
npm install                     # also runs `prisma generate`

# 2. Migrations
npx prisma migrate deploy       # creates the tables

# 3. Seed
npm run db:seed                 # 3 users and 12 sample orders (see Seeded accounts)

# 4. Start the app and the worker, in two terminals
npm run dev                     # terminal 1: app on http://localhost:3000
npm run worker                  # terminal 2: provisions PENDING orders
```

Then open http://localhost:3000 and sign in with one of the seeded accounts below.

`npm install` prints warnings about install scripts "not yet covered by allowScripts" (prisma,
fsevents, unrs-resolver). They are expected and harmless: the Prisma client is generated by this
project's own `postinstall`.

## Seeded accounts

Created by `npm run db:seed` (local development only):

| Role | Email | Password | Lands on |
| --- | --- | --- | --- |
| Admin | admin@example.com | Admin123! | `/admin/orders`: every order, filters, retry |
| Customer | alice@example.com | Customer123! | `/orders`: own orders, "New order" |
| Customer | bob@example.com | Customer123! | `/orders`: own orders, "New order" |

If Chrome autofills a saved login, clear the password field too when switching accounts. Otherwise
the other account's password is sent and you get "Invalid email or password".

## Setup details

**Environment.** `.env.example` holds every setting, with defaults that match `docker-compose.yml`:

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `postgresql://mailbox:mailbox@localhost:5433/mailbox_orders` | App and worker database |
| `AUTH_SECRET` | placeholder | Signs session cookies. Any string of 32+ characters |
| `WORKER_POLL_MS` | `1000` | How often an idle worker checks for PENDING orders |
| `PROVIDER_FAILURE_RATE` | `0.2` | Chance that one mocked mailbox call fails |
| `PROVIDER_MIN_DELAY_MS` / `PROVIDER_MAX_DELAY_MS` | `1000` / `3000` | Mocked provider latency per mailbox |

**Migrations.** `npx prisma migrate deploy` applies the committed migrations in `prisma/migrations`.
If you change `prisma/schema.prisma`, use `npx prisma migrate dev` instead to create a new migration,
then `npx prisma generate`.

**Seed.** `npm run db:seed` creates the three seeded accounts above and 12 orders: ACTIVE and FAILED ones with
a full audit history, and two PENDING ones that the worker picks up as soon as it starts. It is safe
to rerun: it resets the seeded users' passwords and **deletes all of Alice's and Bob's orders**,
including ones you created, before recreating the samples.

## Running

```bash
npm run dev        # app on http://localhost:3000
npm run worker     # provisions PENDING orders; start it in a second terminal
```

- Open the app on `localhost`, not a LAN IP: the create form needs `crypto.randomUUID()`, which
  browsers only allow on localhost or HTTPS.
- Order pages refresh themselves every few seconds while an order is PENDING or PROVISIONING, so
  you can watch the worker's progress.
- **Two workers:** run `npm run worker` in a third terminal as well. Both pick up orders, and each
  order's audit log still shows exactly one `PENDING → PROVISIONING` claim per attempt.
- **Seeing failures:** each mailbox fails with probability `PROVIDER_FAILURE_RATE`, and one failed
  mailbox fails the order. To make failures common:

  ```bash
  PROVIDER_FAILURE_RATE=0.5 npm run worker
  ```

  An admin can then retry the failed order. Only its failed mailboxes are provisioned again.

## Tests

Postgres must be running for the integration tests (`docker compose up -d --wait`).

```bash
npm run test:unit          # no database: state machine, schemas, providers, worker loop, auth, form logic
npm run test:integration   # real Postgres: order creation, idempotency, concurrent claims, worker, API routes
npm test                   # both
npm run typecheck && npm run lint
```

The integration tests use a separate database, `mailbox_orders_test`, on the same server. It is
created and migrated automatically, and your dev data is never touched. It runs in a non-UTC time
zone on purpose, to catch timestamp bugs that a UTC-only setup would hide.

## Troubleshooting

- **Port 5433 or 3000 is in use:** stop whatever holds it, or change the host port in
  `docker-compose.yml` together with `DATABASE_URL` in `.env`.
- **`Can't reach database server` or `ECONNREFUSED`:** check that Docker is running and `docker compose ps` shows the
  database as healthy. `npm run db:check` runs a test query with the app's settings.
- **Start over with an empty database:** `docker compose down -v`, then repeat the quick start from
  `docker compose up -d --wait`.

## Known limitations

- **An order can stay in `PROVISIONING` forever** if a worker crashes, or the database drops,
  in the middle of an order. Nothing reclaims it. The fix is a `claimedAt` lease with
  claim-token fencing, so another worker can take over a stale claim and the old one can no
  longer write. Retrying the final transition alone isn't safe: if the first commit actually
  succeeded, the retry reports a false conflict.
- **Ctrl+C on `npm run worker` stops it at once** instead of letting the order in progress finish.
  The signal reaches the worker twice (directly and passed on by npm), and the worker treats a
  second signal as "force quit". That order then hits the limitation above.
- **Sessions are stateless JWTs (8 h).** Logging out clears the cookie, but a copied token stays
  valid until it expires, and role changes only apply at the next login.
- **A session for a user deleted after login** returns a 500 error instead of 401.
- **`/login?next=` accepts `/%09/evil.example`**, so after login the user can be sent to another
  site (open redirect).
